# ERP Preflight — Known Limitations

> workstream-E verification recorded in `docs/E2E_TEST_REPORT.md`.
> **Rule for this file (spec 0.2, C §64/§75):** only limitations that were observed in the code or in a
> test run are listed; each one names where it lives. When a limitation is fixed, move it to the
> "Resolved" table at the end with the commit that fixed it — do not delete it silently.

## 2. Analysis engines

| # | Limitation | Where / evidence |
|---|---|---|
| E1 | Several engines answer **non-SAP text** with `COMPLETED` and zero findings (they cannot tell "nothing wrong" from "nothing understood"): ACCOUNT_DETERMINATION, CLEAN_CORE, FORM_DOCTOR, IAM_COST, TRANSPORT_DEPENDENCY, WORKFLOW_STUCK. | Observed by the input probes in `ENGINE_CATALOG.md` (generated by `scripts/generate-engine-catalog.py`) |
| E2 | Some engines emit **substantive findings with high confidence for non-SAP text**: OPD_GUARD `OPD_DETERMINATION_STEP_MISSING` (VERIFIED) on a two-line text CSV, ECC2CLOUD `ECC_TCODE_OBSOLETE_REDESIGN` (RULE_DERIVED), MFS_BLACKBOX `MFS_FIRST_CAUSAL_DIVERGENCE` (VERIFIED), EXTENSION_IMPACT `EXT_SAFE_TO_DELETE` (UNKNOWN). A garbage artifact can therefore produce a confident-looking verdict. | `ENGINE_CATALOG.md` → "Input probes" |
| E3 | Clean Core Object Guard is regex-based; spec 07 §7.5 asks for AST analysis (abaplint). | `services/analysis-python/src/engines/clean_core.py` |
| E4 | Five engine modules in `src/engines` are not registered and never run (`fiori_403.py`, `iam_cost.py`, `safe_decommission.py`, `system_refresh.py`, `workflow_stuck.py`); the registry dispatches to their successors. Dead code that can confuse reviewers. | `ENGINE_CATALOG.md` → last section |
| E5 | `decommission_audit` falls back to `date.today()` when no `evaluation_date` is supplied → not byte-for-byte reproducible across days. | `services/analysis-python/src/engines/decommission_audit.py` |
| E6 | Nested archives are rejected instead of being supported to depth 2. | `apps/api/src/modules/ingestion/archive-safety.guard.ts` |

## 3. Security

Full list with owners: `SECURITY_REVIEW.md` §5. Headlines:

| # | Limitation |
|---|---|
| S1 | Leaked Coolify API token and demo-account passwords are in public git history; rotation is an **owner action** and not verified. |
| S2 | No Content-Security-Policy / security headers on the web app; the JWT is kept in `localStorage` (XSS would expose it). |
| S3 | Upload endpoint has no multipart file-size limit (`FileInterceptor('file')` without `limits`) — memory exhaustion risk. |
| S4 | Auth rate limiter is in-memory per API instance. |
| S5 | Agent-gate execution token not bound to the proposal id; signature compare not constant-time. |
| S6 | Webhook signing secrets are stored in plaintext in `webhooks` (and therefore in backups). |
| S7 | `pnpm audit` reports open HIGH/CRITICAL advisories in dev/build tooling (vitest, orval→undici, next→postcss). The CI audit job is report-only until they are fixed. |

## 4. Operations

| # | Limitation | Where / evidence |
|---|---|---|
| O1 | **Single VPS, not highly available** (spec C §56). Postgres, Redis, MinIO, ClamAV, API, web and the analysis service share one Hostinger VPS: any host failure is a full outage; RPO = time since last backup; no failover. Migration path: `DEPLOYMENT_GUIDE.md` §9. | `docker-compose.coolify.yml` |
| O2 | Backups are local to the VPS unless the operator configures the off-site copy (`DEPLOYMENT_GUIDE.md` §7.3). No point-in-time recovery (no WAL archiving). | `scripts/backup.sh` |
| O3 | Migrations run inside the API container start (`infra/docker/api-entrypoint.sh`, `STRICT_MIGRATIONS=true`) rather than as a separate job with an automatic pre-migration backup (spec C §54). A failed migration stops the API container; the operator takes the backup manually first (runbook). | `infra/docker/api-entrypoint.sh` |
| O4 | Observability: structured logs, `/health/liveness`, `/health/readiness` and a token-protected Prometheus `/api/v1/metrics` exist. There is no OpenTelemetry tracing, no Sentry, no Grafana dashboards and no alerting (spec 12.8/12.9, C §57). | `apps/api/src/modules/telemetry` |
| O5 | Compose infrastructure images use floating tags (`elestio/minio:latest`, `clamav/clamav:latest`); the application images are digest-pinned. | `docker-compose.coolify.yml` |
| O6 | ClamAV needs ~3 GB RAM and several minutes to load signatures after a restart; uploads fail closed (HTTP 503) meanwhile. Summed container limits are ~13 GB; 8 GB VPS plans risk OOM. | `docs/runbooks/CLAMAV_DOWN.md` |
| O7 | `services/analysis-python/requirements.txt` includes `pytest` and `pytest-asyncio`, so test tooling ships in the analysis image. | `services/analysis-python/requirements.txt` |
| O8 | Next.js infers the output-tracing root from the nearest lockfile; when the repo is checked out inside another pnpm workspace (e.g. a git worktree) the standalone server lands at a nested path. Images and CI are unaffected; setting `outputFileTracingRoot` in `apps/web/next.config.ts` would make it explicit. | `scripts/ci-live-e2e.sh` handles both layouts |
| O10 | BullMQ ignores `REDIS_URL`: the queue connection is built from `REDIS_HOST`/`REDIS_PORT`/`REDIS_PASSWORD` only, so a database index in `REDIS_URL` has no effect and two API deployments sharing one Redis share `bull:analysis-queue` (jobs of one instance can be consumed by the other). Harmless with the single production stack; wrong for shared staging Redis. | `apps/api/src/app.module.ts` (`BullModule.forRootAsync`) |
| O9 | Not verified here: deployment to the VPS, the release workflow (GHCR push, cosign) and the `live-e2e`/`docker` workflows on GitHub-hosted runners — they were reproduced locally command by command (`docs/E2E_TEST_REPORT.md`). The analysis image's `apt-get` steps could not run in the sandbox (Debian mirrors blocked). | — |
